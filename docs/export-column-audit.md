# Excel export column audit

Audit date: 2026-07-23  
Scope: every workbook generated by the current backend export services.  The
audit follows each displayed column back to the parser field, the source
workbook location, and any transformation performed before the value is
written to Excel.

The reusable decisions behind this audit are documented in
[Reusable Excel-export design standards](excel-export-design-standards.md).

## Conventions

- `OSIP_ПОРТФЕЛЬ` references below are physical Excel columns (A=1), not
  zero-based Python indexes. Rows are the immutable source-row references
  retained with each lot/cash/event.
- A value shown as `Недоступно` means the source did not provide a usable
  value. It is never a zero and is never filled with a guessed calculation.
- ISIN is the aggregation key for instrument, distribution, and lot views.
  Repeated lots remain separate in `Позиции по лотам` and `Лоты источника`.
- `Расчётная стоимость`/`MV` is operational carrying value, not official NAV
  or market value. Its formula is `AA × AU × AT + AR` per lot, then summed:
  carrying amount in native currency (AA), report FX (AU), principal
  indexation (AT; blank means 1), plus accrued income in KZT (AR).
- The dashboard's own carrying-value calculation uses the OSIP report FX
  field. The only export-only KZT/USD presentation conversion uses the dated
  National Bank of Kazakhstan USD/KZT RSS rate, with the source-reported OSIP
  rate as an explicitly labelled offline fallback.

## Workbook navigation standard

Generated Excel exports use one consistent navigation rule. A continuous table
sheet freezes every row from the top through the first table header row and
freezes column A, so the labels remain visible during both vertical and
horizontal scrolling. In `openpyxl` this is `B<header_row + 1>`; when the
first header happens to be row 6 it appears as `B7` in Excel. The header row is
calculated from the sheet rather than hard-coded because exports can have
different title/metadata lengths.

Stacked multi-section sheets such as `Распределения` do not have one header
that should remain pinned over unrelated sections. They therefore freeze only
column A (`B1`). Any future workbook generator should use the shared table
helper or explicitly document a deliberate exception here.

Module summary/dashboard sheets (e.g. `Сводка ФО`, `Сводка по лимитам`) and
the module-level `Данные графиков` chart-helper-data sheet are a further,
deliberate exception: no freeze at all. These are read chart-first, not
scrolled as a long table, so a frozen column A has nothing to do there.

exceptions register the standard calls for. `assert_workbook_is_compliant`
(`tests/export_compliance.py`) enforces the freeze rule, plus error-cell,

below; see §7 for exactly what it checks and its known limitations.

## OSIP holdings export (`/holdings/export`)

### Sheet: `Инструменты`

| Excel column | Source / formula | Audit result |
|---|---|---|
| Код инструмента | OSIP F (`security_code`) | Direct source value. |
| ISIN | OSIP G (`isin`) | Direct source value; primary key for aggregation. |
| Эмитент | OSIP I (`issuer`) | Direct parsed value; issuer normalization is presentation-only. |
| Истинный класс актива | OSIP H/E plus the checked-in ISIN dictionary | Dictionary may refine the workbook section (e.g. SGOV/TIP ETF → government bonds). Raw class remains in source evidence. |
| Валюта | OSIP M (`instrument_currency`) | Direct source value. |
| Лоты | Count of persisted source rows for the ISIN | Source-row count, not a new calculation. |
| Количество | Sum of OSIP Q by ISIN | Aggregation by ISIN; exported as an integer-formatted number. |
| HPR (расч.), KZT, % | `(derived carrying value KZT − purchase amount KZT + received dividends KZT after tax + estimated paid coupon KZT) / purchase amount KZT × 100` | Explicit KZT percentage-point result. The gross 360-day coupon estimate is reduced by the current accrued coupon already present in carrying value, preventing double-counting; future coupons are excluded. |
| HPR (расч.), FX, % | `(derived carrying value USD − purchase amount USD + received dividends USD after tax + estimated paid coupon USD) / purchase amount USD × 100` | Explicit FX percentage-point result using the USD-equivalent basis where supported and the same non-overlapping coupon estimate in native currency. For KZT lots the common FX factor cancels; other currencies remain unavailable rather than being silently rescaled. |
| Текущая YTM, % | OSIP Z (`current_ytm`) in percentage points (for example, `16.70` means `16.70%`) when all lots for the ISIN agree | If lot values conflict or are absent, `Недоступно`; no averaging. |
| Расчётная балансовая стоимость, KZT / Сумма покупки, KZT | Sum of `derived_carrying_value_kzt` or OSIP V (`purchase_amount_kzt`) according to the selected basis | Exact selected-basis total. |
| Вес, % | Selected-basis value divided by filtered selected-basis total | Typed Excel percentage; total row is checked and displays the validation result. |

The total row is calculated from the same filtered rows displayed above it, so
the table total and the control sheet cannot silently diverge.

### Sheet: `Позиции по лотам`

This is the row-level view behind the ISIN aggregation. It preserves one row
per source lot. `Стоимость покупки, ₸` is always the source purchase amount,
while `Текущая стоимость, KZT`, `MV, USD`, and `Вес, %` continue to use the
selected valuation basis named in the title. These columns are therefore not a
claim of independent market pricing.

| Excel column | Source / formula |
|---|---|
| Код инструмента, ISIN, Эмитент | OSIP F, G, I |
| Дата погашения облигации | OSIP O (`close_date`); for repo rows this is the source close date when present |
| Истинный класс актива | Same ISIN dictionary and mapping as the main holdings sheet |
| Валюта цены | OSIP M; native currency for the two unit-price columns |
| Количество, Номинал | OSIP Q, L |
| Стоимость покупки, ₸ | OSIP V (`purchase_amount_kzt`), always source purchase cost regardless of the selected valuation basis |
| MV, USD / Текущая стоимость, KZT | Selected basis: OSIP V for purchase, or derived `AA × AU × AT + AR` for carrying value |
| Лот № | Stable display sequence after sorting by code, ISIN, and source row; not a source identifier |
| Дата открытия | OSIP R (`purchase_date`); falls back to OSIP N only when R is absent. N is the instrument's issue/open date, not the portfolio ownership date. |
| Цена покупки за единицу (источник) | OSIP S (`purchase_price`); OSIP does not state a universal quote scale |
| Стоимость открытия | OSIP U (`purchase_amount_native`) |
| Накопленные купоны или дивиденды, KZT | OSIP AR (`accrued_income_kzt`) for bond-like rows plus validated Bloomberg dividends converted to KZT; `Недоступно` when neither component has a supported value |
| Оценка выплаченных купонов или дивидендов (валюта цены) | Estimated paid coupon (`max(gross estimate − current accrued coupon in native currency, 0)`) plus validated Bloomberg dividends in the instrument's price currency; approximation for coupons, not proof of payment |
| Текущая балансовая цена за единицу (источник OSIP) | OSIP Y (`carrying_price_native`, «Балансовая цена»); clean price (%) for bonds and accounting-currency price for equities/repos. If the legacy `.xls` cell contains the OSIP formula but no cached result, the parser reproduces `IF(Q=0,0,IF(OR(AA=0,ISBLANK(AA)),"",IF(BF=4,AA/Q,IF(BE=3,AA/Q,AA/Q/L*100))))` using the source row. |
| HPR (расч.), KZT / FX | Derived carrying value minus purchase amount plus received dividends after tax and estimated paid coupon in the named currency basis; FX uses the USD-equivalent basis | Dividend eligibility is evaluated per lot using its purchase date and the current calculation date. The paid-coupon estimate subtracts the accrued coupon already included in carrying value, so that field is not counted twice. |
| HPR (расч.), KZT, % / FX, % | Each named-currency HPR amount divided by that currency's purchase amount × 100 | Both are percentage points, not Excel fractions; the KZT and FX bases are explicit in the header. A KZT lot's FX percentage can remain numeric because a common FX factor cancels, while its USD amount may still be `Недоступно`; non-KZT/non-USD currencies remain unavailable. |
| Текущая YTM, % | OSIP Z, already expressed in percentage points; exports quote the `%` sign without multiplying by 100 |

### Sheet: `Ожидаемые денежные потоки`

`Предстоящие расчёты` rows are intentionally excluded.  The export contains
only events represented by the current portfolio rows:

| Excel column | Source / formula |
|---|---|
| Код инструмента | OSIP F |
| Тип потока | `Погашение` from OSIP O close/maturity date, `Купон` from OSIP AM next-coupon date, or `Дивиденд (Bloomberg)` from the dividend dictionary |
| Дата | OSIP O/AM for instrument flows; Bloomberg `pay_date` for expected dividends |
| Сумма (maturity) | OSIP L nominal × Q quantity when both exist; otherwise `Недоступно` |
| Сумма (coupon) | OSIP AN `Сумма ожидаемого купона`, read as a source value; no coupon formula is invented |
| Сумма (dividend) | Bloomberg dividend × lot quantity, net of 15% when ticker contains a standalone `US` token; only when `ex_date > purchase_date` and `pay_date` is inside the window |
| Валюта | OSIP M; dividend amount remains in the lot's instrument currency |

Expected dividend rows are sourced from the active Bloomberg dividend
dictionary (`sources/dividends.xlsx` or the uploaded replacement). They are
cash-flow estimates, not OSIP settlement records. The export note reports the
dictionary freshness; future payments are included by `pay_date` only when the
lot was held on its `ex_date`, and US-listed amounts use the existing 15%
withholding rule.

The view is bounded to the inclusive interval from the snapshot's report/as-of
date (the generated workbook date) through that date plus 180 calendar days.
Rows are sorted by event date ascending, then instrument code and flow type for
stable ordering. This is a reproducible snapshot rule: it does not use the
machine's current date or parse a date from the filename. Events without a
date are omitted because their membership in the window cannot be established.

### Sheet: `Распределения`

All four tables use the same filtered ISIN rows as `Инструменты` and the same
selected basis.  Each total row is checked against the main-sheet total.

| Table / column | Source / formula |
|---|---|
| Currency / MV, ₸ | Selected-basis KZT value grouped by OSIP M |
| Currency / MV, $ | USD lots use their source native amount; KZT lots use selected KZT value divided by one common dated USD/KZT rate |
| Currency / Вес, % | Selected-basis weight grouped by currency |
| True class / MV, ₸ and weight | ISIN dictionary true class grouped by selected-basis value/weight |
| Risk / MV, ₸ and weight | Dictionary `Rating group` (with rating buckets and equities/commodities categories) grouped by selected-basis value/weight |
| Focus/sector/factor / MV, ₸ and weight | Dictionary `Focus/sector/factor` grouped by selected-basis value/weight |

The `MV` label is a presentation convention inherited from the requested
layout; the metadata and disclosure explicitly state the selected basis and
that the value is not official market value.

### Sheet: `Контроль и происхождение`

`Итоговая стоимость, KZT`, `Итоговый вес`, `Ожидаемый вес`, `Разница`, and
`Статус проверки` are controls over the filtered `Инструменты` rows.
`Количество ISIN` is the number of rows in that aggregated view.  The
provenance table lists each ISIN, code, issuer, workbook, sheet, and source
row(s).  OSIP field-level provenance is available through the API metric
provenance; the Excel export keeps the human-friendly row-level references.

## Findings and corrections

1. The standalone OSIP lot export previously used the broad workbook section
   class, so dictionary-backed true exposure (notably government-bond ETFs)
   could disagree with the holdings export. It now uses the same ISIN
   dictionary mapping and labels the column `Истинный класс актива`.
2. Percentage-valued lot fields are now labelled explicitly as
   `Доходность покупки, %` and `Купон / ставка РЕПО, %`.
3. The multi-source raw exporter resolves `record_type` from the dataset record
   rather than the payload, so client summary and position rows are no longer
   indistinguishable.
4. Expected coupon values are read from OSIP AN and shown only for rows with a
   next-coupon date; missing source values remain `Недоступно`.

## Remaining provenance limitation

Multi-source dataset records currently persist workbook/sheet/row references,
not a per-field source cell for every normalized field. The raw JSON/formula
payload remains retained for investigation, and OSIP has an exact parser
column map above. Adding exact cell coordinates to every multi-source field is
the next provenance enhancement; no export currently claims a cell-level
reference where only row-level evidence is stored.

## Verification

- The backend export/API test suite verifies sheet order, headers, typed
  numbers/dates, filters, totals, dictionary true-class allocation, source
  references, publication gating, and the brokerage client-data allowlist.
- Run `pytest -q` from the repository root after any export change.
- Open generated workbooks with `openpyxl` using `data_only=True` and inspect

## Cell-level audit (2026-07-23)

This pass audited every *class of populated cell* produced by the exporters,
including fixed metadata cells, dynamic table rows, totals, validation cells,
source-reference cells, chart-data cells, chart ranges, number formats, and
empty/unavailable-value handling. Because row counts and source columns are
dynamic, an audit of an arbitrary future workbook cannot list literal row
numbers in advance; the ranges below describe the complete generated layout.

### OSIP workbook cell map

| Sheet | Fixed cells and metadata | Dynamic populated cells | Control / derived cells | Traceability |
|---|---|---|---|---|
| `Инструменты` | `A1:K4`: title, portfolio, report date, version, basis, search/class filters, disclosure and weight check | Header row `6`; instrument rows `A7:K(6+n)`; each row is one ISIN aggregate | Total row immediately after the data rows contains selected MV and summed weight; weight status is written in the metadata block | ISIN aggregation is source-backed; exact source rows are listed on `Контроль и происхождение` |
| `Распределения` | Title/metadata and weight check in `A1:D4` | Four independent tables (currency, true class, risk, factor), each with its own header, rows and total row | MV and weight are grouped from the same filtered ISIN view; true class/risk/factor are dictionary-derived | Source rows are represented by the control-sheet provenance registry, not copied into every distribution cell |
| `Позиции по лотам` | Title/metadata, operational-price disclosure and weight check | Header row `6`; one row per selected source lot, including generated display lot number | Purchase-cost total and weight after the lot rows; the current balance price is the OSIP `Балансовая цена` source field, not a rescaled market quote | Each lot retains workbook, sheet and source row; generated lot number is not a source identifier |
| `Ожидаемые денежные потоки` | Title/metadata, Bloomberg freshness note, and explicit unavailable-amount disclosure | ISIN-grouped maturity/coupon rows plus expected Bloomberg dividend rows inside the report-date + 180-day window | Dividend rows use `pay_date`, require `ex_date > purchase_date`, and apply 15% US withholding; maturity/coupon sums remain `Недоступно` when source fields are absent | OSIP rows retain their source lineage; dividend rows identify Bloomberg in the flow type and are covered by the active dictionary metadata |
| `Контроль и происхождение` | Title and control labels | Control values and one provenance row per ISIN/code | Total value, total weight, expected weight, difference, validation status and ISIN count are static typed snapshot values | Workbook/sheet/row references are aggregated here; cell-level OSIP column mapping is documented above |
| `Данные графиков` | Title and chart-grouping note | Separate editable chart-source blocks for each distribution table | “Прочее” is a chart-only materiality grouping; presentation tables remain complete | Native charts reference these cells, not hidden ranges; editing this sheet changes charts only |

All OSIP numeric cells are typed `Decimal`/numeric values with explicit formats:
integer lots and quantities, two-decimal HPR, two-decimal YTM and monetary
values, and percentage weights. `Недоступно` is a deliberate text value, not a
zero. Formulas are neutralised before saving, so totals and controls are
readable by a non-recalculating workbook consumer. Auto-filters cover the data
rows only; totals deliberately sit outside the filtered range and therefore do
not pretend to be dynamic Excel formulas.

### Cell-level findings

1. **Brokerage export intentionally now also carries the Clients domain.** The
   brokerage route bundles `client_account_snapshot`, `client_open_dates`,
   `client_maturity_calendar`, and `client_dashboard_snapshot`, and writes an
   `Аналитика клиентов` summary alongside the brokerage one. This was a
   deliberate scope change (the Brokerage and Clients exports were merged into
   one workbook, hosted from the Brokerage tab; the Clients tab no longer has
   its own export button) - not a boundary violation. The raw trade sheet
   itself still enforces its non-PII allowlist (`client_name`/`account`/`iin`/
   `counterparty` are excluded from `Сделки`); only the separate client-domain
   sheets carry client data, same as when they were exported on their own.
2. **Exact cell provenance is incomplete for multi-source exports.** Those
   sheets identify source workbook, sheet and row, but not the original column
   letter/cell for each normalized field. The raw payload is retained, and OSIP
   has an exact column map, but a user opening a source drawer cannot yet jump
   directly to (for example) `Лист8!M109` for every field.
3. **Totals are snapshot values, not live formulas.** This is intentional for
   reproducible exports, but filtering an Excel table does not recompute the
   total row. The control/validation text is the authoritative check.
4. **Mixed-currency totals are deliberately partial.** Currency-summary native
   amounts and calendar native amounts are not summed across currencies; only
   like-currency rows or KZT-known totals are aggregated. This is correct, but
   the disclosure must remain visible.
5. **Charts and presentation tables have different edit paths.** A user edits
   the presentation table without changing the chart, because the native chart
   references the final `Данные графиков` sheet. This is transparent and
   editable, but should be stated near the chart-data sheet.
6. **Weights are scoped to comparable populations.** A currency-turnover
   weight uses the sum of available National Bank of Kazakhstan KZT
   equivalents for that buy/sell side. A raw trade weight uses the native
   amount within the same currency and side. The exports do not fabricate one
   percentage across mixed currencies or incompatible event rows.
