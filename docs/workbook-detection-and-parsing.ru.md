# Определение типа рабочей книги и разбор данных

Как приложение определяет тип загруженной рабочей книги (workbook), какие
листы обязательны для каждого типа и какие строки/столбцы используются при
разборе данных.

## Как работает определение типа (диспетчер)

Каждая загруженная рабочая книга проходит через `detect_source()` в
[multi_source/__init__.py:257](../backend/osip_dashboard/ingestion/multi_source/__init__.py#L257).
Сначала читается только **список названий листов** (дёшево, без разбора
ячеек), затем перебирается фиксированный, упорядоченный список контрактов
(`_CONTRACTS`, строка 243) — побеждает первый, чей `propose()` вернул не
`None`. Порядок важен: два контракта запускаются от одного и того же листа
(см. примечание про Бухгалтерию ниже). Если ничего не подошло, вся загрузка
отклоняется с ошибкой `SourceDetectionError`.

Отдельно стоит **портфельный снимок OSIP в старом формате `.xls`** — он не
проходит через этот диспетчер вообще: разбирается напрямую функцией
`parse_osip_workbook()` в `osip_workbook.py`, тип запускается на уровень выше
(выбором типа импорта), а не определением по листам.

Ниже: «обязателен на 100%» — без этого листа определение типа падает.
«Опционален» — определение типа всё равно проходит успешно, просто этот
конкретный набор данных не предлагается. При первом упоминании каждого
листа в скобках указано, что на нём физически находится — **не полагайтесь
на название листа как на признак содержимого**: несколько шаблонов
рабочих книг переиспользуют одни и те же общие названия («Лист1» и
подобные) для совершенно разных данных в разных книгах (см. лист `Лист1`
ниже — наглядный пример).

## 1. Портфельный снимок OSIP (`osip_workbook.py`)

**Обязательный лист:** `ОСИП_ПОРТФЕЛЬ` (содержит: одна большая таблица —
построчно все позиции портфеля — ISIN, тип бумаги, эмитент, номинал,
рейтинги, даты, балансовая/рыночная стоимость и ещё ~30 полей, — плюс
строки денежных остатков вперемешку с позициями) — должен существовать под
точным названием ([osip_workbook.py:147](../backend/osip_dashboard/ingestion/osip_workbook.py#L147)),
иначе вся рабочая книга отклоняется.

**Поиск заголовка, а не фиксированная строка:** парсер сканирует столбец A
сверху вниз в поисках буквального текста `"№"`, затем проверяет, что в этой
строке по названиям столбцов находятся `isin`, `security_type` и `quantity`
(`_REQUIRED_HEADER_FIELDS`). Эта строка становится заголовком; всё остальное
считается относительно неё, а не по жёстко заданному номеру строки — это
намеренно, поскольку генератор OSIP менял раскладку листа посреди работы
над проектом уже не один раз (столбцы вставлялись, менялся порядок).

**Все остальные поля** (~35 штук — ISIN, ставка купона, балансовая
стоимость, рыночная стоимость, даты и т. д.) определяются **поиском по
тексту заголовка** (`_FIELD_LABELS`), а не по позиции столбца. Поле, чья
подпись не найдена, считается просто «недоступным», а не ошибкой разбора —
жёстким сбоем является только отсутствие трёх обязательных полей заголовка.

**Классификация строк ниже заголовка** (по содержимому, не по номеру
строки):
- Строка, чья подпись начинается с `"ОСТАТОК ДЕНЕЖНЫХ СРЕДСТВ"` → строка
  денежного остатка.
- Строка с пустым `security_type` или нулевым/пустым `quantity`, но
  непустой подписью в столбце A → **заголовок раздела** (например,
  «Корпоративные облигации»), запоминается для последующих строк.
- Строка с `quantity > 0` → строка позиции (лота).
- Строка с `quantity < 0` → строка расчёта (предстоящей сделки).

Лист также обязан содержать ≥83 столбцов (`EXPECTED_COLUMN_COUNT`), иначе
отклоняется как усечённый.

## 2. Бухгалтерия (`multi_source/accounting.py`) — 4 отдельных контракта в одной книге

**a) Баланс + отчёт о прибылях и убытках** (контракт `accounting_statements`):
- **Обязательно:** лист `f1_uip` (содержит: бухгалтерский баланс —
  построчно статьи актива/обязательств/капитала, код строки, суммы за
  текущий и предыдущий период), и он должен буквально содержать текст
  `"Бухгалтерский баланс"` где-то на листе (одной проверки названия листа
  недостаточно — именно эта проверка текста отличает настоящую
  бухгалтерскую книгу от файла, в котором просто случайно есть лист с
  именем f1_uip).
- Баланс: читается `f1_uip`, отчётная дата из ячейки `A3`, строки данных
  начинаются со **строки 11** (строка 11 — это сам заголовок раздела
  «Активы»; ранее здесь была реальная ошибка на единицу, уже исправлена).
  Столбцы: A = наименование, B = код строки, C = текущий период,
  D = предыдущий период. Раздел отслеживается сопоставлением текста
  столбца A со значениями `{"активы", "обязательства", "собственный
  капитал"}` на строках без кода. Разбор останавливается на первой строке,
  чья подпись начинается с «примечан» (раздел примечаний).
- Отчёт о прибылях и убытках (**опционален**, лист `f2_uip`, содержит:
  построчно статьи доходов/расходов, код строки, суммы за квартал/с
  начала года и те же два показателя за аналогичный период прошлого
  года; предлагается только если есть этот лист): отчётная дата из `A4`,
  строки данных с 12-й;
  столбцы A/B/C/D/E/F = наименование/код/квартал/с начала года/прошлый
  квартал/прошлый период с начала года.

**b) Бюджет** (контракт `accounting_budget_landing`):
- **Обязательно:** лист `Бюджет` (содержит: три раздела подряд на одном
  листе — отчёт о прибылях и убытках, ОДДС, баланс, — каждый со своими
  строками-статьями и колонками план/факт за 2023, 2024, 9 мес. 2025,
  помесячно и т. д.), содержащий текст «бюджет» либо «2026».
- Дата на конец периода из ячейки `F66`. Строки сканируются с 4-й; строка
  относится к разделу (`income_statement`/`cash_flow`/`balance`), когда её
  подпись начинается с текста-маркера («отчет о прибылях и убытках» /
  «оддс» / «баланс»); далее каждый раздел читает фиксированные столбцы от
  B до Z (2023, 2024, бюджет/факт за 9 мес. 2025, помесячно янв.–дек. и
  т. д. — 26 фиксированных позиций столбцов, `_BUDGET_PERIOD_COLUMNS`).

**c) Детализация портфеля** (контракт `accounting_portfolio_landing`):
- **Обязательно:** одновременное наличие листов `ОСИП_ПОРТФЕЛЬ` (в этой
  книге — та же таблица позиций/остатков, что и в разделе 1: тот же
  генератор/шаблон, тот же набор столбцов) **и** `Лист1`. `Лист1` здесь
  используется **только как признак типа книги** — его содержимое никогда
  не разбирается на данные; по факту (проверено на реальном файле
  `Бухгалтерия_Портфель.xls`) на нём лежит сводка портфеля — разбивка «По
  виду ФИ» и «По отрасли» (похоже на лист с диаграммами/сводной
  таблицей, почти все ячейки пустые).
  ⚠️ **Название `Лист1` не уникально для этого контракта.** В отдельной,
  никак не связанной книге истории стоимости пая (раздел 3 ниже, «История
  паёв») точно так же есть лист с названием `Лист1` — но там на нём лежит
  **список цен по инструментам** (тикер/название/цена/валюта/дата), то
  есть то же название листа означает совершенно другие данные в другой
  книге. (Этот `Лист1` для контракта истории паёв сейчас вообще не
  проверяется — раньше требовался, но `_parse_unit_history` его не читает,
  см. комментарий в коде.) Мораль: название листа само по себе ничего не
  говорит о содержимом без контекста конкретной книги.
  (Это и есть признак, отличающий данный контракт от отдельного
  контракта OSIP ниже, который тоже срабатывает по одному наличию
  `ОСИП_ПОРТФЕЛЬ` — наличие `Лист1` проверяется *раньше* по порядку
  контрактов, поэтому книга с обоими листами никогда не распознаётся
  ошибочно как обычный снимок OSIP.)
- Данные начинаются со строки 4 (строки ≤3 пропускаются); столбцы
  определяются по тексту заголовка, а не по фиксированной позиции (то же
  семейство генератора, что и у OSIP, то же исправление хрупкости). Строки
  группируются под текстовыми заголовками категорий; отслеживание
  категории прекращается при обнаружении подписи из ЗАГЛАВНЫХ букв вида
  `"ПО ..."` (блок остатков по банкам).

**d) Режим только «свидетельства» (landing)**: любая бухгалтерская книга,
подошедшая под один из контрактов выше, дополнительно получает набор
`accounting_landing` — он вообще не разбирает бизнес-данные, а лишь
сканирует каждый лист на предмет дат, ошибок формул (`#REF!`/`#N/A`) и
внешних ссылок — исключительно для аудита/проверки.

## 3. Фонд / TABYS — оценка стоимости (`multi_source/tabys.py`)

**Обязательный лист:** `дата` (содержит: плоская таблица
«наименование показателя → значение» — СЧА, стоимость пая, стоимость
ценных бумаг, деньги на счетах и т. д., по одному показателю на строку),
и на нём должен буквально присутствовать
текст `"Текущая стоимость портфеля ЦБ"` — проверяется раньше всего
остального.

- Лист `дата`: строки 1–41 читаются как плоская таблица
  «наименование → значение» (столбец A = наименование, столбец D =
  значение) — этот единственный лист лежит в основе наборов данных
  `fund_valuation`, `fund_cash_liabilities` и `fund_inactive_evidence`.
- `часть 1 (портфель)` (**опционален**, содержит: реестр позиций фонда —
  порядковый номер, эмитент/вид бумаги, ISIN, количество, дата постановки
  на учёт, дата погашения, валюта и номинал; включает `fund_holdings`):
  данные с 6-й строки.
- `Цены` (**опционален**, содержит: список цен по инструментам — тикер,
  название, последняя цена, валюта цены, дата котировки; включает
  `fund_prices`): данные с 3-й строки.
- `справка о ст-ти ЧА` (**опционален**, содержит: показатели СЧА по дням —
  даты идут колонками, а не строками; строки — показатели вроде «Остаток
  на инвестиционных счетах», с разбивкой по валютам; включает
  `fund_nav_history`): все строки.

**История паёв — отдельный контракт** (`fund_unit_history`, **отдельная
загружаемая книга**, не связанная с тремя листами выше): требует лист
`Форма` (содержит: дневной ряд по стоимости пая — дата, количество паёв в
обращении, число пайщиков, СЧА и стоимость пая в USD и в KZT),
содержащий текст `"# Паев в обращении"`. Строки данных начинаются
с 4-й. Эта книга тоже может содержать лист с названием `Лист1` — см.
предупреждение о неуникальности этого имени в разделе 2c выше; здесь он
сейчас не проверяется и не используется контрактом.

## 4. Клиенты / Брокеридж (`multi_source/client_brokerage.py`)

**Обязательный лист:** `Лист4` (содержит: реестр лицевых счетов и позиций
клиентов — счёт, имя клиента, ИИН, гражданство, резидентство, затем по
каждому счёту — позиции по бумагам: эмитент, тип и т. д.), и он должен
содержать текст `"Л/счет"`. Это единственный по-настоящему обязательный
лист — всё остальное является сопутствующей детализацией, каждая часть
опциональна независимо:

| Лист | Содержит | Включает набор данных | Дополнительное требование |
|---|---|---|---|
| `Лист4` | реестр счетов и позиций клиентов (см. выше) | `client_account_snapshot` | обязателен, строки с 7-й, отчётная дата из области `[1,6]` |
| `Лист8` | реестр сделок — № сделки, № заказа, дата, площадка, клиент, счёт, контрагент, сторона, эмитент, тип бумаги, ISIN, количество, сумма, валюта, чистая/грязная цена, доходность | `brokerage_trade_ledger` | должен содержать «Номер клиентского заказа» |
| `Лист7` | реестр производных инструментов — № сделки, дата/время, дата расчёта, тип инструмента, идентификатор, площадка, базовый актив, контрагент, вид сделки, количество, цена, сумма, валюта, статус обязательства | `derivatives_register` | строки с 15-й, отчётная дата из `A9` |
| `Лист6` | справочник дат открытия счетов — используется только для сверки имён клиентов с `Лист4`, не как отдельная витрина данных | `client_open_dates` | строки со 2-й, сопоставление с `Лист4` со строки 7 |
| `календарь погашения` | предстоящие погашения/выплаты купонов по клиентским позициям — клиент, менеджер, бумага, дата погашения | `client_maturity_calendar` | строки со 2-й, сопоставление через справочник позиций `Лист4` |
| `Клиенты` | сводка по клиенту — имя, менеджер, тип клиента, дата открытия, остаток денег и т. д. (агрегат на уровне клиента, не на уровне счёта/позиции, в отличие от `Лист4`) | `client_dashboard_snapshot` | строки с 3-й, также используется для восстановления недостающих имён менеджеров в `Лист4` |

Столбцы на каждом листе определяются по тексту заголовка, а не по
фиксированной позиции.

## 5. Корпоративные финансы (`multi_source/corporate_finance.py`)

**Обязательно:** в рабочей книге должен быть **ровно один лист** (содержит:
реестр сделок/мандатов — эмитент, предмет договора, объём размещения,
фактически удовлетворённый спрос, инвесторы, ставка и размер полученного
комиссионного вознаграждения, длительность проекта), и он
должен содержать текст `"Направление корпоративного финансирования"`.

Текст периода — из `B2`; строки данных с 5-й; столбцы определяются по
тексту заголовка (`_corporate_finance_columns`).

## 6. Риски (`multi_source/risk.py`) — два отдельных контракта

**SOBSTV:** требует одновременного наличия листов `Лимиты` и `Лимит по
странам` (оба — фиксированные названия, дополнительная проверка текста не
нужна — сами эти два названия считаются достаточно уникальными).
- `Лимиты` (содержит: перечень инструментов инвестирования — пороговые
  значения лимита в % от собственных активов, утверждённый лимит в
  деньгах, фактическое значение в %): заголовок ищется в первых 6
  строках, отчётная дата — из листа
  `Лимит по странам`, строка 2, столбец C. Строки данных распознаются по
  числовому маркеру (целое/дробное) в столбце B.
- `Лимит по странам` (содержит: страна, статус страны, лимит в USD и в
  KZT, фактический размер инвестирования по стране): заголовок в первых 4
  строках, требуется ≥21 столбец на строку.
- `Лимит на Эмитента` (наименование эмитента, инвестировано в тенге,
  лимит в тенге, инвестировано/лимит в % от базы, направление лимита),
  `Лимит на Отрасль` (то же самое, но по отрасли GICS вместо эмитента),
  `Лимит по МСФО` (классы финансовых инструментов по бизнес-модели МСФО,
  утверждённый лимит в % и в деньгах, фактическое значение), `Лимит по
  дюрации` (позиции ценных бумаг с разбивкой по типу/резидентству/
  стране/отрасли/валюте, далее модифицированная дюрация против лимита),
  `Расшифровка` (построчная расшифровка денежных остатков и вкладов —
  тип инструмента, конкретный банк/счёт, валюта, сумма в валюте, курс),
  `Detail` (то же самое по смыслу, но сгруппировано по стране — валюта и
  суммы по категориям инструментов на страну) — **все опциональны**,
  каждый включается независимо по своему наличию в `workbook.sheet_names`, у
  каждого — своё окно поиска заголовка (4–6 строк) и своя минимальная
  проверка количества столбцов на строку.

**TABYS:** требует лист `Пр2-16` (содержит: «Отчёт о соблюдении
(использовании) установленных лимитов инвестирования» — классификация
инвестиции, установленный лимит в % и фактический размер в % и в KZT,
сигнал соблюдения). Отчётная дата разбирается из 4-й строки
(`rows[3][1]`, диапазон в формате дд.мм.гг). Столбцы заголовка ищутся в
первых 10 строках; на листе — семь разных разделов «По ...» в одной
сплошной таблице, различаемых по тексту-маркеру раздела в столбце A,
строки помечаются измерением (country/currency/issuer/instrument_category/
sector/fx_position/instrument_issuer).

## Общая закономерность для всех типов

**Названия листов обязательны на 100%** (точное совпадение строки, иногда
плюс дополнительная проверка текста внутри листа для отличия похожих
файлов), но **позиции столбцов почти никогда не жёсткие** — каждый парсер
здесь определяет столбцы поиском известного текста подписи (на русском
языке) в строке(-ах) заголовка, потому что генератор источника менял
порядок столбцов минимум по разу на каждое семейство рабочих книг за
реальную историю этого проекта, а чтение по фиксированному индексу молча
прочитало бы неверные значения вместо явного отказа.
